# 主动服务真实体验测试方案：过去一周的使用历史与持续观察

日期：2026-11-24。状态：本轮已完成；正式观察2026-11-24 04:33:27至11-25 04:34:11（Asia/Shanghai），约24.012小时，含约36分29秒Docker故障缺口。最终结论与证据在被Git忽略的 `.local/proactive-realworld/20261124/`。两个隔离测试账号主动服务已关闭，数据保留；到期唤醒、离线新通知等未覆盖项已明确记录，不等于全场景通过。

## 1. 测试的核心

**给它一段连贯、真实感足够的过去一周使用历史，然后让它继续陪伴这个用户，观察它会不会在合适的时候，带来真正有用的主动关心。**

这不是要求系统在某一分钟发出某一句话的脚本验收，也不是主要检查主动服务内部的计时逻辑。主要站在外部用户的视角判断：它有没有理解这个人的处境、有没有主动发现可推进的事情、是否懂得克制，以及它提出的内容是否可信、及时、能用。

主会话收到主动消息与没有收到主动消息都可能合理。不能把“没有消息”直接判为失败，也不能把“发出了消息”直接判为成功。另一方面，持续不触达也不能天然解释为聪明的克制，需要结合真实背景和可发现的机会评估。

本方案已按用户授权进入执行 Goal：启动隔离项目和真实 Web 客户端，构建历史、持续观察并形成结论。本轮不修改被测主动服务的策略或产品实现。

## 2. 测试对象和边界

### 2.1 主要观察什么

- 它是否把多个会话看成同一个人的连续生活与工作，而不是互不相关的问答。
- 它能否从尚未明确交办的背景里发现机会，而不只是复述用户已提出的问题。
- 它能否结合最近变化重新理解事情，而不是机械追踪过期目标。
- 它是否在有事实、有价值、有时机的情况下触达，且能解释与用户的关系。
- 没必要打扰时，能否安静地等待，而不是制造寒暄或反复发送同一建议。
- 主动内容是否真正出现在主会话，并在用户离开页面后仍能正常回看。

### 2.2 不作为这次的中心

不为测试修改 AgentLoop、系统提示词、触发窗口或业务策略；不强制它调用某个工具、安排几分钟后的检查或一定通知。不开启手机推送测试，不把 Schedule 的显式提醒当成自主发现成功。

实现日志用于记录证据和必要时定位问题，不作为主要评分对象。只有外部表现异常时，再逐步检查它是没有运行、信息未进入、研究失败、作出了不触达决定，还是决定投递但没有展示。

## 4. 历史数据不是只有聊天文本

### 4.1 需要准备的一整套材料

每个会话包含完整的原生 Session 日志。用户和助手消息只是其中一部分，其他材料包括：

- 消息接纳与执行推进的原生事件、实际存在的 turn/step 记录。
- 助手文字、工具调用及参数、工具结果、失败与纠正、结果提交和正常结束记录。
- 与日志引用匹配的工作目录、生成文件、图片附件、显式交付记录。
- 有需要时的历史检索、记忆读写、时间上下文。
- 插件贡献的 Skill、CLI 或 MCP 工具被实际使用的过程。
- 插件安装、启用和凭证的当前可用状态；这类状态仍保存在它们本来的存储中，不假装所有管理操作都是 Session 事件。

不另造一种“主动服务测试专用会话格式”。用现有原生会话格式生成、存储、加载和回放这些材料。

保留过去一周的完整历史，不等于把全部内容强行注入每次后台运行。由产品正常获取近期信息、记忆和必要的历史检索，测试的是它自然利用这些材料的效果。

### 4.2 参考执行流程与真实执行记录的关系

下文逐轮写的是**参考执行流程**，不是只有参考回复。它描述正常使用时会发生哪些可观察动作、需要哪些工具或插件、产生什么结果，以及助手最后应该如何交代。

这份流程不限定模型的逐步内部推理，也不把工具顺序写成唯一答案。比如真实 Agent 多做一次文件检查、先搜再浏览或先加载 Skill，都可以合理。

历史构造阶段允许使用预先编排的助手与工具调用请求，以获得连贯的模拟历史；能够执行的工具应实际执行并记录返回值，不能把理想结果直接当作工具执行成功。正式观察阶段全部使用真实模型自主运行，不使用预写的研究结果、触达结论或下一次检查时间。

预置材料统一标记为**模拟使用历史**，不声称用户过去真的进行过这些操作。正式观察部分另标记为**实时运行记录**。

### 4.3 过去一周如何安排

以正式观察开始时间为 `T0`，历史范围是 `[T0−7天, T0)`。一周是滚动的七天，不固定绑定本文日期。所有场景使用 Asia/Shanghai 的用户语境，并保留明确日期、时间及时区。

表中 `D−6` 代表 T0 所在日期往前六天；同一天不同时段的轮次按正常交流节奏排列。最早记录不贴七天边界，避免执行准备耗时导致它意外落出范围。

最后一批消息使用相对 T0 的过去时间；执行时统一展开成真实日期，不能因为 T0 恰好在凌晨就生成“今天上午”这种尚未发生的历史。用户提到的“明天”“下午三点”必须与那轮模拟时间一致。最后一两天的交流把仍在进行的事情留给未来观察，其余事情允许已经完成、取消或改变方向。

构造方法：在隔离的历史准备环境完成工具执行，保留实际返回值和文件；用现有 v4 序列化、加载与校验能力构建过去一周的历史记录。日期编排只发生在启动目标 Host 前，不在它运行时编辑日志，也不改生产运行时的时钟。涉及时间的事件、time-context、场景文件及 Schedule 参数要语义一致；不对 JSONL 做无差别字符串替换，不伪造不匹配的 checkpoint。可派生的索引和运行投影由正常加载重建。

转入正式观察前必须验证：日志可完整加载、会话可回放、附件能打开、文件能下载、已完成工具不会被恢复流程重做、各会话的工作目录正确。未通过时只修复测试数据构造，不能带病开始评价主动服务。

## 5. 主测试用户的连贯背景

模拟用户：**林舟**，杭州一家约 18 人的 B2B 软件团队的产品负责人。团队计划做一个小范围 AI 助手试点。林舟需要读资料、向同事汇报、控制预算；同一时间还要准备一次上海客户交流，日程比较满。

他习惯中文交流，接受清楚标明来源的英文资料；希望建议短而具体，不喜欢泛泛的鼓励或每天固定问候。工具和权限没有替他决定的权力：不代发邮件、不采购、不订票、不把草稿分享给外部。

以下是编排依据，不是一整段直接塞给后台的额外“用户画像”提示词。这些背景应通过各会话和真实记忆材料自然形成。

## 6. 过去一周的完整参考会话与执行流程

主账号共 **8 个会话、92 轮**。每轮给出用户原话和参考执行流程，流程中的最终回复内容是交代重点，实际历史中的文字可按执行结果自然组织。

会话长度有意不平均：行业研究 17 轮、试点推进 23 轮、Office 交付 20 轮，其余会话为 4～8 轮。三个长会话跨多天推进，包含范围澄清、来源核对、文件迭代、用户纠正、版本区分、阶段收尾和仍未解决的问题。十几轮、二十几轮都是正常的自然使用长度，这些数字是当前编排，不是会话长度上限；不把一个问题拆成无意义的“继续”来凑数量。

| --- | --- | --- |

加上对照账号的 6 轮，共 98 轮用户交流。这里“一轮”按一次用户输入及其对应的 Agent 执行计算；一个执行可以有多个 step、工具调用和助手消息，不能把 98 轮理解成只有 196 条事件。

每个长会话都保留早期依据和后来的修正，按时间交错地发生在同一周。长会话不能按目录逐个全部生成后再硬塞错误时间：例如 A3 使用 A1 的资料、A2 的试点边界时，所引用的文件必须已经在更早的历史时点存在。实际构造按全账号时间表执行，跨会话时序和文件版本一起核对。

依赖前文具体措辞的追问要跟随实际历史分支。例如前面没有声称“十条通过”，后面就改为“我们确认一下：检查文件结构不等于已经验证十条回答，对吗？”，不能捏造助手此前说错了什么。保持这轮交流的真实意图，不强迫实际回复逐字匹配参考。

不是每一轮都需要工具或更新记忆。短回答、拒绝过度承诺、停止继续扩展和确认已完成同样属于真实使用过程。错误和纠正只在实际发生或用户真实更正表述时记录，不为制造复杂执行流而添加假的工具故障。后台仍使用现有的有界资料与历史检索；本方案不为长会话提高上下文采集上限，也不把全部历史强塞进每次后台运行。

### 8.1 模拟过去的后台检查，形成当前 proactive.json

按最新要求，正式观察以“过去已经检查过，现在继续运行”的状态开始，而不是第一次看见全部用户背景。

在一周的时间线上选择最近一次检查时间 `Tc`，默认约为 `T0−6小时`，并核对它确实位于一组会话交流之间。若真实 T0 所在时段使日内安排不自然，可调整 Tc；最终以已展开的全账号历史时间表为准。Tc 前还要有第 8.2 节所述的连续后台研究历史，不能只孤立构造最后一轮。

1. **先截取当时能看到的材料**：只读时间不晚于 Tc 的会话前缀、当时已有的记忆与文件版本。不能用 Tc 之后的最新消息替过去的 Agent 作决定。
2. **模拟这一轮已完成的后台检查**：给专用后台 Session 生成匹配的原生执行日志，包括当时的时间与背景、可观察的检查过程、structured_output 的实际结果形状以及正常 turn 结束。该轮明确标记为历史模拟，不计入实时观察成果。
3. **生成同一个决定的状态投影**：使用真实后台 Session ID、主会话 ID、该轮编号和模拟开始/完成时间；nextCheck 的时间及理由必须与这轮日志中的结构化结果一致。初始建议是依据当时任务节奏，在 T0 之后约 40～60 分钟继续查看，而不是写“为了测试所以很快检查”。最终决定依照 Tc 时的信息确定，不为保证正式观察触达而设置。
4. **继续放入 Tc 后的普通会话**：保留较新的优先级变化、任务收尾、取消安排等。若这些变化按现有规则构成待检查信息，就相应设置 pendingChange 和最后变化时间；不能把后来的变化错误标成已被上轮消费。
5. **启动后只让正常机制接管**：在 Host 停止的准备阶段完成日志与状态落盘，并将账号期望状态设为已启用；正式启动恢复这份已有状态，不靠反复开关主动服务制造初始化运行。可能发生正常到期检查，也可能因待处理的新信息先检查，两者都如实记录。

状态文件位于 Host 的 `/root/harness/.dsh/storages/proactive.json`。这里不新增格式或字段，沿用当前 State；ResultTurn 与后台已提交的结构化结果对应。选择不触达的历史分支时，不伪造主会话消息，也不留下虚假的待投递记录。若实际决定需要历史投递，则必须补齐对应的真实原生投递事实，不能只填 deliveryMessageId。

本轮默认先采用有合理不触达依据的历史检查：当时资料仍在整理、用户未确定是否有新需要，记录发现并安排下次检查。这个选择只有在 Tc 前的材料支持时才成立，不能预写一个理想的业务判断作为未来答案。

验收时同时看三份材料：**Tc 前能看到什么、该轮检查决定了什么、proactive.json 当前记录了什么**，并列明 Tc 后尚未被本轮检查覆盖的新消息。用于下一次时间判断的历史理由与实时观察中的真实结果严格区分。

| H2 | D−3 晚间 | 来源表、部分模拟样本和 Word 修订已存在，内部会议尚未发生 | 读取 H1 之后的变化，必要时检查真实文件和已有来源；继承上轮研究而不是从头重复；区分准备材料与效果已验证 |
| H3 | Tc，约 T0−6 小时 | 当时已经发生的汇报和试点信息，以及 H1/H2 的研究历史 | 更新当前理解、收束已完成事项，决定是否值得触达，并产生启动时使用的 nextCheck；不得预知 Tc 后的取消和新优先级 |

参考时间需要展开后验证严格递增、落在过去一周内。若准备耗时改变 T0，所有模拟时间和相对日期一起复核。各轮具体发现和触达决定由其可见材料支持，不能为了制造漂亮案例指定每轮都有发现或必须通知。

每次历史检查至少保留：当时的时间上下文、唤醒输入、运行时背景、当时模型可见的系统提示/工具组合、助手可观察的研究文字、工具调用与参数、实际结果或明确标记来源的模拟检索结果、后续步骤、结构化决定和 turn 结束。完整日志中的原生种类按当前实现产生，不强行新增事件来承载这些描述；模型可见视图从同一日志按正常机制恢复，不另存一份互不一致的“完整上下文”。

网页搜索不要求使用用户的搜索凭证：可由测试助手核对公开来源，准备有来源和时间说明的检索材料，再作为**模拟历史中的工具结果材料**使用。它不冒充正式观察期的真实 websearch 调用。能够实际执行的文件、浏览器和插件操作仍尽量执行，结果要能核对。此项覆盖主会话与后台历史准备阶段。

H2 可以看到 H1 的真实模拟输出，H3 可以看到 H1/H2；每次注入的外部资料只取该时点之前的信息。需要进一步检索旧会话时，记录实际使用的锚点/片段。不能将后面一周的完整计划或未来脚本一起放进早期上下文。

如某轮模拟决定触达，必须补齐其主会话内部投递、主会话 Agent 的正常承接流程与可见回复，并按过去的时间放回整个历史；如不触达，则研究过程只存在后台 Session 中。两种情况都不计入正式观察成绩。

正式启动前必须确认：后台 Session 能完整恢复；历史 turn 已正常结束、不会恢复后重新执行旧工具；H3 的已提交结果与 proactive.json 的 Session ID、轮次、完成时间、nextCheck 等逐项一致；过去已投递的内容不被重复投递；待投递状态只有在确有完整待投递事实时才存在。后台需要的早期上下文按产品本来的保留和 compaction 机制处理，不能为了测试绕过它。

交付时，seed 目录单独包含后台原生日志、每次历史检查当时的输入材料清单、模拟/实际执行来源说明，以及 H3 到当前状态的对应关系。后续实时产生的后台研究日志保留在 runtime 目录，清楚标出二者分界。

正式后台 Agent 能否实际使用某个插件，仍由现有可见能力决定。我们不为让案例成功而额外扩大它的工具权限。

### 8.3 多事项关注与完整执行上下文

后台 Agent 不限定每轮只关注一件事；同一轮可以兼顾试点、客户交流和工作节奏，也可以在一次触达中呈现多个值得说明的事项。一次 `notify` 是一次投递载体，正文可包含多个发现；`nextCheck` 是该后台 Agent 下一次整体检查的时间，不是每件事分别建立的任务。评估不要求它每轮罗列全部背景，也不把“一次只说一件最及时的事”视作失败。

历史准备的实现方式为：测试助手编排模型响应，通过隔离 Host 的原生 Agent 执行流程形成日志。后台检查使用产品原有后台会话、运行时背景、时间上下文、工具与结构化结束机制。前一次检查完成后继续准备后续普通会话，再构造下一次检查，保证早期检查没有读到未来交流。保存各 step 的模型请求视图，用来核对系统提示、工具组合、过去研究与本轮工具结果确实进入了上下文。

后台历史的验收单位是一次完整的检查流程，不是若干用户/助手消息：唤醒与时间输入 → 当时背景采集 → 可观察研究 → 实际工具调用与结果 → 后续 step → `structured_output` 成功结果 → 正常 `turn/end`。历史日期仅在隔离 Host 停止后统一投影到过去一周，并验证日志关系、时间上下文和最后状态一致；原始准备执行记录另行保留。它不冒充过去真实运行过的模型研究。


## 9. 正式观察节奏

### 9.1 默认观察一天，先完成一个四小时检查点

建议总观察时间 **24 小时**，包含工作时段、安静时段和次日再打开。前 **4 小时**完成第一个可独立交付的检查点；若自然检查机会少，则如实记录覆盖不足，再延长，不能为了凑轮次偷偷缩短系统时间。

不保证几小时内必有主动消息，也不承诺在无人维持测试环境、电脑休眠或服务停止时仍算连续观察。运行中断需要记明起止时间，恢复后另行计算实际覆盖。

### 9.2 阶段安排

| 阶段 | 主要动作 | 外部观察重点 |
| --- | --- | --- |
| 历史准备 | 生成过去一周的模拟使用历史，准备对应文件与插件，正式主动观察暂不开启 | 账号像一个真正使用过产品的人，历史能完整加载 |
| T0 | 按第 8.1 节恢复已启用的历史状态，在 Web 正常登录；之后离开主会话，不发送“请主动关心我”之类测试指令 | 它会不会自然理解背景；不以初始化一定触达为目标 |
| T0～T+90 分钟 | 不新增交流，让它自然运行 | 安静是否合理；有研究/触达时，是否与当前试点相关 |
| T+90 分钟附近 | 按下文选一段新交流，通过普通会话真实发送并等正常回复 | 新信息是否改变后续关注点，而不是沿用旧方向 |
| T+90 分钟～T+4 小时 | 再次等待，期间正常切换会话和离开网页 | 自主选择的跟进是否自然；是否只有盯着主会话才看得到消息 |
| 四小时检查点 | 汇总已发生的机会、主动内容、沉默和证据 | 给出阶段性判断，不为“已跑四小时”强判成功 |
| T+4～T+12 小时 | 根据已有结果只加入一次自然收尾或纠正，之后安静 | 是否停止追踪取消事项、减少重复提醒 |
| T+12～T+24 小时 | 保持 Host 在线，浏览器可以断开；次日重新打开主会话 | 是否按用户背景继续；内容能回看，不出现历史丢失或重复展示 |

这些时间是测试人员的日程，不是传给后台 Agent 的检查计划。真实触达时机由产品决定。准备耗时、工具调用速度和自然对话长度可以使人工操作时间略有浮动。

### 9.3 观察期间的新交流脚本

只按需要加入下列自然交流，不全量连续灌入，也不把“如果正确就提醒我”等预期答案写给 Agent。

**N1：新信息，让旧关注点发生变化。**

在 A2：
> 刚跟同事聊了一下，他们最担心的不是模型费用，而是回答时引用了旧版本文档。我们不准备马上换模型，想先把资料版本和回答依据弄清楚。这个先记下来，我要去开个会。

参考执行流程：正常记录这条实际约束；可以更新已有笔记，不能擅自创建后续任务。未来主动内容若仍只推荐便宜模型，需要评估它是否忽略了新的优先级。

**N2：关闭一个机会。**

在 A2，N1 的问题已经被处理或相关触达已出现后：
> 文档版本的问题同事已经接手了，今天会把旧版移出试点目录。先不用继续研究这个点。接下来我只想按现有十条样本跑一遍，再看哪里有问题。

参考执行流程：确认负责人已接手和目标收敛；不再继续扩张同一个问题。允许没有主动通知。

**N3：普通短交流，不代表新任务。**

在 A5：
> 刚刚出去走了一小会儿，清醒多了。我准备把今天剩下的一点时间用来把已有东西收尾。

参考执行流程：自然回应，不推断健康问题、不建立固定休息提醒。它可以辅助理解用户状态，但不意味着必须启动一轮关心。

N1 是计划中的一次主要变化；N2 和 N3 根据实际时间和观察结果使用。新增交流本身由真实模型正常回复并生成完整原生执行日志，不只写两条聊天文本。

### 9.4 Schedule 的位置

本轮主要账号不靠 Schedule 制造主动触达。若需要单独验证“用户明确安排的任务”和“自主发现”的区别，可在后续扩展批次用第三个隔离账号创建一次真实提醒，单独标记结果。

不增加业务去重规则，不要求后台必须避免在相近时间说话。评估的是内容对用户是否重复、冲突或多余，而不是额外发明产品中不存在的机制。

## 10. 从外部体验出发的评价标准

### 10.1 七个维度

每项采用 `0 / 1 / 2 / 未覆盖`，用于组织判断，不把总分当成自动通过线。

| 维度 | 0：明显问题 | 1：基本合理 | 2：比较好的体验 |
| --- | --- | --- | --- |
| 理解这个人 | 串错人、记反偏好、把旧目标当当前目标 | 主题相关，能遵守主要约束 | 能自然连接不同会话中的目标、时间和限制 |
| 自主发现 | 复述前一轮或空泛提醒 | 带来一项有用整理 | 找到用户未明确提出、但确实有帮助的新联系或证据 |
| 研究可信度 | 编造来源、结论夸大、声称做了却没做 | 来源可复核、局限说清楚 | 证据与建议对应，知道什么尚未证实 |
| 时机与分寸 | 无关打扰、取消后继续追、制造焦虑 | 合理触达或合理安静 | 在有意义的时间点出现，并明显降低用户负担 |
| 具体可用 | 看完不知道能做什么 | 有一个具体建议或发现 | 清楚说明为什么与用户有关，以及下一步如何使用 |
| 连续性 | 重复说同一件事、无视用户后来的更正 | 能延续并更新关注点 | 逐步推进而非反复从头研究，知道何时收尾 |
| 表达与交互 | 混淆用户发言、伪装用户主动提出、页面丢内容 | 主会话显示清楚，重开能回看 | 主动内容自然进入对话，引用与附件可用，后续追问顺畅 |

评估不把主动提醒的篇幅长短作为问题，不设置字数阈值，也不因内容详细而降低评价。重点判断相关性、准确性、可用性和触达时机；只有冗余重复、偏离用户目标或增加不必要工作时，才按相应问题评价。

这些判断关注公开可观察的内容，不要求 Agent 展示隐藏推理。后台可见日志和已提交结果用于核实有没有遗漏，不把“写了很长的理由”当作合理的充分证据。

### 10.2 对“没收到消息”的判断

每个观察区间都用同一组问题复盘：

1. 当时有什么真实未解决的需要？是否已经被用户关闭或交给他人？
2. 是否存在可以查证的新信息或明显有帮助的跨会话联系？
3. 用户现在知道这件事，会有合理的用处吗？还是只会多出一个新坑？
4. 这一段是否真的发生过可评估的运行机会？如果没有，是否因为它安排的后续时间尚未到达，或环境中断？
5. 若它决定不触达，这个决定与公开背景是否一致？

结果分类为：**合理安静、可能错过机会、尚无充分观察机会、运行/服务故障**。不能把四者混在一起。

机会清单由测试人员独立记录，例如“已完成的汇报不应继续催改”“新发现文档版本风险可能比换模型更值得关注”。它不是一份唯一标准答案；具体通知内容可以完全不同，只要同样可信、相关和有用。

### 10.3 对“收到消息”的判断

逐条记录：实际出现时间、用户当时在做什么、原文、它依据的已知背景、新增了什么、来源是否存在、用户需要花多大注意力。

一个值得肯定的结果可以是：把跨会话约束整理为少量可执行检查；找到与试点直接相关的原始资料变化；发现已有文件里可避免的真实风险。它不必是一条新闻，也不要求所有运行都上网搜索。

明显不好的结果包括：泛泛问候、重复用户刚说的话、硬件新品推荐、已取消的出差提醒、用户叫停后仍推研究、把未经证实的产品承诺说成已验证、为了“主动”擅自发送外部消息或创建任务。

## 11. 如何持续观察而不干预它

以主会话的正常用户视图作为第一证据。配一个**测试侧只读观察器**，记录运行期间的公开会话事件、主会话新增内容、连接状况和必要状态快照；观察器不向 Agent 发消息、不创建产品 Schedule、不改它的下一次检查。

仅在出现新结果、自然运行失败、明显重复研究或计划中的人工观察节点时详细查看，避免高频人工提问把“被动等待”变成持续驱动。

至少覆盖以下 Web 操作：

- 在另一个会话停留时，主会话的新内容能正常被接收，并在进入后看到。
- 关闭测试浏览器页面后等待，再打开主会话，新增内容能从正常历史回放获取。
- 主会话收到内容后，以用户身份追问一次“这和我现在的试点有什么关系？”或“这点我先不做”，观察后续是否能自然接住。
- 不使用浏览器是否在线推断用户是否有空；不要求有系统级通知。

如果没有真实主动内容，不伪造一条来完成截图；保存当时正常页面及观察事实即可。若确实需要另外验证投递协议，另建标明为模拟的功能测试，不混进这次真实体验结论。

## 12. 证据、目录和隐私

测试生成内容放在被忽略的本地目录，不把批量历史、私有配置或大文件提交到开源仓库。建议目录：

```text
.local/proactive-realworld/<run-id>/
  plan-copy.md
  scenario/                 # 用户原话、参考执行流程、过去一周的时间表
  seed/                     # 模拟历史的完整原生日志、文件/附件清单
  runtime/                  # 实时观察期导出的完整原生会话日志
  observations/             # 按时间记录外部表现、覆盖和中断
  screenshots/              # Web 原始截图，保留必要页面上下文
  report.md                 # 人能读懂的体验结论
  manifest.json             # 版本、时间、场景与文件校验、模型及工具统计
```

场景文案和报告不含密钥、OAuth token、私有模型请求头或真实个人账号数据。完整日志按私有测试资料管理，公开分享的截图和摘要另做检查。

保留**完整的 Session 执行事实**；分析时再提取用户/助手消息、实际工具调用、输出和阶段性结论。不能反过来只存摘要后声称已有完整执行数据。

## 13. 成本、停止条件和缺陷处理

- 先做一个完整账号 A 加小型对照 B，不一开始并行很多用户。
- 历史构造可以用预编排模型请求，降低纯背景材料的生成成本；真实工具结果必须核对。正式主动观察必须用真实模型和真实可用服务。
- 记录模型调用、工具调用、外部服务请求及可获得的 token 用量。正式执行前确定本轮可接受的费用预算，不能把“持续观察”解释为无上限调用。
- 发现重复失败而无新尝试、持续重复搜索而无新信息、异常高频运行或明显费用异常时，记录证据并停止相应测试账号，作为运行质量问题报告。
- 不为了得到一条漂亮通知临时修改提示词、植入理想证据或反复开启关闭主动服务。
- 发现产品问题先保留原始结果，区分事实、判断和可能原因；另开修复批次。修复后是新一轮结果，不能覆盖掉首次失败记录。
- 本次不做破坏性故障注入或修改其他真实用户的 Host，不用停止生产服务来检验恢复。

## 14. 最终交付与结论形式

执行完成后交付：

1. **过去一周的完整测试数据集**：多会话用户和助手内容，以及对应 Agent 执行流程、工具记录、文件/附件和插件相关状态清单。
2. **实时运行时间线**：什么时候有新交流、什么时候自然出现研究结果、什么时候主会话收到内容、什么时候安静、哪里有中断。
3. **主动触达逐条评审**：有价值、一般、重复、打扰、错误、待进一步验证；每项有原文与来源。
4. **沉默区间评审**：合理安静、可能漏掉的机会、没有足够观察机会或服务故障。
5. **真实 Web 截图**：展示实际发生的交互，不编造成功案例。
6. **产品判断**：目前是否像一个了解用户、会做事且有分寸的助手；主要问题出在背景理解、研究能力、时机、表达还是可靠性；下一轮优先改哪一两项。

最终不使用“运行了多少轮”“发了多少条消息”作为核心成绩。即使只出现一条主动消息，如果它真实、及时、与用户有关且降低了负担，也可以比十条泛泛关心更好；反过来，一天都没有消息也需要解释清楚究竟是克制、机会不足，还是系统确实没有发挥作用。
