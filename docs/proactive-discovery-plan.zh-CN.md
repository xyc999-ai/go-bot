# Go Bot 主动服务方案：自主判断、唤醒与触达

日期：2026-11-22。状态：已实现，完成本地 Go、Docker、真实模型及 Web / Android Release 验收。本文已按本轮讨论整体更新，取代上一版中的首次交流门槛、固定检查区间、主会话二次价值判断和子 Agent 自动回报设计。

本文确定运行主体、触发、结果、投递，并细化其他会话资料的采集和上下文归属。完整实施契约见第 13 节；现有 Go 装配及执行边界见[架构说明](architecture.md)，统一 Go Preset 的设计与实施记录见 [Go Agent Preset 方案](agent-preset-go-plan.zh-CN.md)。

## 1. 主体与职责

主动服务是 **Go Host 内置、独立管理的后台 Agent**，有自己的 Session、历史、turn 和运行上下文。它承担自主研究、下一次检查时机判断，以及是否需要触达用户这三个责任。

**执行机制直接复用现有 AgentLoop。** 不修改 turn/step 推进、Inbox 接纳与领取、工具执行管线、结束判断、checkpoint 或 compaction；不增加后台 Agent 专用的循环分支。下文的唤醒、资料收集、结果捕获和投递均位于 Agent 组装、标准工具或外部服务层。

它不通过普通 `fork` / `subagent` 工具创建，不复制主会话全部历史，不使用普通子 Agent 的自动结束回报链。它与主会话有明确的投递关系，但不是一次用户临时委派的子 Agent。

| 模块 | 职责 |
| --- | --- |
| 后台主动服务 Agent | 阅读背景、研究、自主判断下一次时间、自主决定是否触达 |
| Go 主动服务运行模块 | 接收触发、恢复 timer、驱动这个 Agent、校验并提交结果、完成实际投递 |
| 主会话 Agent | 收到已决定触达的内部消息后，正常向用户表达结果，不再做第二次价值筛选 |
| 长期记忆与历史检索 | 提供用户背景和历史事实；继续使用现有实现 |
| Schedule | 继续处理已保存的工作安排和投递，也是 AI 可读取的工作信息 |
| 插件 | 提供工具、Skill、外部信息和可选变化提示，生命周期继续由 Cordis 管理 |

Schedule 与主动发现之间的业务关系由 AI 理解，不增加代码层业务去重或另一份交办事项表。

## 2. 为什么使用一个持久后台 Agent

| 选择 | 评价 |
| --- | --- |
| 再创建独立的唤醒 Agent | 需要维护两个 Agent 的背景、历史与交接；当前没有充分理由增加它 |
| 独立一次 LLM 调用专门安排时间 | 可以实现，但每次需单独组织背景；不作为每次运行后的必经步骤 |
| 同一个持久后台 Agent 处理时间重评和自主研究 | 推荐；它已有上下文，可按本次输入决定是否研究、是否只调整时间 |

Agent 本身仍使用普通模型调用和工具调用循环。所谓“时间重评”是一种本次运行的目的，不是另一个进程或必然存在的第二次模型调用。信息足够时，可以一次模型调用就提交结果；需要调查时，可以继续调用工具和进入后续 step。

## 3. 谁触发判断

LLM 在未运行时不能自己调用自己，必须由外部服务提供执行机会。默认触发来源收口为：

| 触发 | 含义 |
| --- | --- |
| Host 就绪 / 模型变为可用 | 没有已保存决定时，启动一次初始判断；有有效决定时按恢复规则处理 |
| 用户关闭后重新开启主动服务 | 立即提供一次检查机会，不受 10/30 分钟变化窗口限制；重复同步已开启配置不触发，普通 Host 重启仍恢复既有安排 |
| 已保存的下一次时间到达 | 后台 Agent 按原先理由重新查看当前情况 |
| 新交流、记忆变化或插件提供新信息 | 记录“有新信息待检查”的标记及最近变化时间，仅这条触发路径使用 10 分钟稳定窗口和 30 分钟最小运行间隔 |

不提供显式“立即运行”触发入口。

不设置“必须首次交流后才开启”的门槛。即使尚无真实对话，也可以在模型可用后运行初始判断；AI 自己判断当前信息是否足够，以及是否等待新信息。预置欢迎消息应有正确来源，不能被当作用户表达了某个兴趣。

新交流、记忆变化和插件新信息先记录“有新信息待检查”的标记，在变化触发条件满足后提供一次执行机会。标记不保存消息正文或内容差异。后台已在执行时，仍可由现有上下文入口在自然进入的后续 step 读取更新；资料刷新不会人为制造一个新 step。

后台自己的普通输出、检查记录、工具返回和主会话对主动投递的回复，不反复触发它自己。

### 3.1 变化触发：10 分钟稳定窗口 + 30 分钟最小间隔

任意普通会话的新交流、相关记忆变化和插件新信息都可以设置待检查标记，并更新最近变化时间。这里只记录窗口调度所需的状态；正文仍在原会话、记忆文件或插件来源中，真正运行时再读取最新资料。无需缓存变化正文、建立变更队列、保存内容差异或按消息数量计数。

- **稳定窗口为 10 分钟**：从最近一次外部资料变化开始计算；窗口内又有变化就重新计算，不立即运行后台。
- **最小运行间隔为 30 分钟**：变化触发的运行，距离最近一次后台实际开始运行至少 30 分钟；不足时保留变化，等待满足条件。
- 没有待检查标记时，窗口机制本身不触发后台，也不每 30 分钟周期运行。
- 待检查标记存在且满足两个条件时，提供一次后台运行机会，开始时实时读取当前已提交的资料。
- 后台正在运行时不并发启动自己；新资料可在自然进入的后续 step 被读取，运行期间又有变化则继续记录待检查标记。

变化路径的最早可运行时间为：

```text
max(最近一次资料变化时间 + 10 分钟,
    最近一次后台运行开始时间 + 30 分钟)
```

首次还没有后台运行记录时，只计算稳定窗口。30 分钟以最近一次实际后台运行开始时间为基准，不论那一次由哪条路径触发；但这个限制只检查变化路径，不能反过来拦截其他路径。

### 3.2 窗口机制不影响其他触发

- AI 已选定的检查时间到达时，即使尚未稳定 10 分钟，或距离上次运行不足 30 分钟，也按时间触发执行。
- 初始化和恢复需要的运行按各自规则处理，不等待变化窗口。
- 用户明确从关闭切到开启时，立即检查一次，再由 Agent 提交新的下一次时间。Controller 常规配置同步和 Host 重启不冒充这次用户操作。
- 原有 Schedule 的到期投递和执行完全不受这个窗口影响。
- 各路径仍遵守同一个后台 Agent 不并发执行、Host 关闭和模型不可用等基本运行条件；窗口不增加其他路径的额外等待。

例如，后台 10:00 开始过一轮，外部最后一次变化在 10:08，变化路径最早为 10:30；若 AI 先前安排的检查时间是 10:15，仍在 10:15 运行。这次实时采集前已有的待检查标记可以消费，不再为旧标记补跑；采集后又发生变化时保留新的标记。

**任一触发路径的实际运行，都刷新同一个运行基准并消费已有待检查标记。** 具体含义：

- 运行真正开始时，更新最近一次后台运行开始时间；变化路径之后的 30 分钟间隔从这里计算。
- 本轮正常完成实时资料采集后，消费采集前已有的待检查标记，不再为它保留一轮单独的变化触发。
- 如果采集后没有新交流、记忆或插件信息，保持无待检查标记；不会到原窗口时间再运行一次。
- 采集后又发生实际变化时，重新设置待检查标记并记录新的最后变化时间，再按 10/30 分钟条件计算。
- 后台运行本身不更新最后变化时间，也不凭空启动一个新的 10 分钟稳定窗口。只收到触发信号、尚未真正运行或资料采集失败时，不能当作已经完成检查并消费标记。

接上例：10:15 运行并采集后没有新信息，则 10:30 不补跑。如果 10:20 出现新的实际变化，则稳定窗口到 10:30，而 30 分钟运行间隔到 10:45，变化路径最早为 10:45。期间另一个独立时间触发仍可先运行，并同样刷新上述基准。

标记表示“需要给后台一次检查机会”，不表示承诺逐条处理每一个变化事件。它不维护每条消息已读/未读、逐个来源的消费回执或业务覆盖表；有界资料仍按后文范围实时收集。消费标记时不能盲目清掉之后新出现的变化标记。

两个窗口值是内置默认策略，不新增用户必须填写的环境变量；不增加消息分类模型或独立唤醒 Agent，也不修改 AgentLoop。

### 3.3 触发信封与实际资料分开

建议唤醒输入只携带 `reason`、发生时间，以及受影响的 `sessionId` / 日志 `seq` 等定位信息，不再完整复制用户消息正文。

实际正文由 Go 上下文采集器在运行时从源会话的已提交日志统一读取，作为一份带来源的活动资料交给模型。采集器按近期活动、消息时间和内容预算选择片段，不读取一份“暂存变化内容”。未展开资料的会话/锚点提示属于本次采集结果，不是窗口机制额外维护的变更列表。

```text
前台会话 / 记忆 / 插件提供新信息
  → 更新待检查标记和最近变化时间（不缓存正文）
  → 变化路径满足 10 分钟稳定窗口和 30 分钟间隔

AI 先前选择的时间到达 / 初始化
  → 独立触发，不受上面窗口约束

任一路径获得运行机会
  → Go 读取最近活跃会话的实际资料，组装本轮上下文
  → 后台 Agent 领取唤醒输入，开始模型执行
  → Agent 按需要继续调用工具获取更多内容
```

“外部负责触发”不能理解成不给任何初始资料、要求尚未运行的模型先自行组装自己的请求。Go 负责首次模型请求的资料组织，Agent 负责运行后的理解、选择、进一步检索与研究。不在模型运行前再增加一个 LLM 做资料整理。

## 4. 下一次时间由 LLM 结合背景决定

每次运行都应能看到：当前背景、上次检查结论、先前安排的时间及原因、本次触发理由，以及需要获取的最新信息。信息分层和有界活动采集按第 10 节执行。

AI 可以：

- 保留原时间。
- 本轮获取新信息后，把下一次时间提前或推迟。
- 在本轮继续研究，然后再安排下一次时间。
- 认为无需近期再查时，仍选择一个更晚的检查时间，并说明理由。

因此不采用固定“30 分钟检查一次”，也不把“每次固定延迟 4 小时”作为业务决策。即使没有新交流，已保存的时间到达后也能主动查询外部信息。

每轮结束前，模型必须通过 `structured_output` 提交非空的 `nextCheck`，包含绝对未来时间 `at` 和非空理由 `reason`，例如 `2026-11-22T09:30:00+08:00`。Go 解析后以 Unix 毫秒保存。`nextCheck` 不允许缺失或为 `null`，也不允许用“等待变化”代替下一次检查安排。主动服务持续运行；即使不触达或暂时无事可做，也由 AI 安排较晚的下次检查。是否关闭服务由用户开关决定。

Go 校验时间格式、是否是未来时间、时区表达和资源条件；它不替 AI 推断合适的业务时机。若模型建议无法执行，应返回明确原因，让 Agent 调整，而不是静默改成另一套固定周期。暂时没有模型、Host 已停止或资源预算耗尽时，运行状态应明确说明。

## 5. 计时器和恢复

一个 Host 保存一个主动服务的下一次运行时间。Go 根据最近决定设置 timer，收到新决定时替换 timer。timer 到达只负责驱动后台 Agent，具体工作继续由 AI 决定。

恢复时：

- 已保存将来时间：恢复 timer。
- 已保存时间已经过去：合并成一次检查机会，不补跑每个错过时段。
- 待检查标记和窗口时间一并恢复；变化路径可以早于 AI 已安排的时间运行，成功结果会替换原检查时间。
- 主动服务被明确暂停：继续暂停；普通交流不会隐式恢复它。
- 从未产生有效决定：模型可用后启动初始判断。

Controller 不轮询所有账号，也不为此添加 Redis 定时任务队列。Schedule 继续运行自己的已有机制；主动服务不向 Schedule 登记一批内部跟进任务。

## 6. 结果在同一个 turn 内结构化提交

后台 Agent 可以在自己的会话中正常思考、查询并产生文本。它必须在结束本轮前调用 `structured_output`，一并提交本轮结论、下一次检查安排和是否触达的决定。复用现有结构化结束机制，提供主动服务专用 schema；不在 turn 结束后再发起安排时间的模型调用。

例如：

```json
{
  "workSummary": "检查了近期报告讨论与新发布资料，确认有一项会影响报告结论的更新。",
  "nextCheck": {
    "at": "2026-11-22T09:30:00+08:00",
    "reason": "届时再查看目前尚未发布的官方材料。"
  },
  "notify": {
    "message": "请直接向用户说明这项更新及其对报告结论的影响，并附上已核实的来源。",
    "evidence": []
  }
}
```

`workSummary`、`nextCheck`、`notify` 三个字段均必填。`nextCheck` 必须为对象，`at` 必须是带时区的未来 RFC 3339 时间，`reason` 必须非空。缺失、`null`、无效或已过期时间在工具执行时返回可修正错误，不设置结束标记；Agent 可以在当前 turn 内修正并重新调用。`notify` 可以为 `null`，表示本轮不触达；可以有有价值的研究结论，但仍选择不触达。`workSummary` 是后台工作记录，不因其存在就投递。是否触达与选择下一次时间是独立决定；无论是否触达，都必须安排下一次自主检查。

字段结构通过本次 `structured_output` 的 schema 声明，并由既有通用工具管线校验；例如将 `nextCheck` 声明为必填对象后，`null` 就会被原管线拒绝。晚于当前时间等动态业务条件由 `internal/proactive/Output` 补充校验：成功后才调用原工具保存结果和 `ConcludeTurn`，失败走既有普通工具错误反馈。这不是通用 AgentLoop 增加的步骤；普通会话和 workflow 子 Agent 不增加 `nextCheck` 约束。

这里的 `message` 是给主会话的内部交付内容，应自洽并包含足够事实；不是让主会话重新调查“是否值得公开”。`evidence` 是证据引用数组，每项包含 `title` 和 `reference`（URL、会话消息锚点或实际文件路径）；没有证据时可以为空数组。内部交付只提供文本事实及引用，不新增图片/文件交付协议。

不要求先完成自由文本 turn，再额外调用另一个 LLM 重新解析它。模型在本 turn 中直接调用结构化结束工具，Go 接受成功提交的参数。

## 7. structured_output 的真实机制与后台适配

当前 Go 已有基础实现，见 `harness/tools/native_structured_output.go`：

```text
模型发起 structured_output 工具调用
  → 执行器校验该次工具参数
  → 工具暂存结果，设置 ConcludeTurn 标记
  → 工具结果成功提交并落盘，确认捕获
  → 当前工具批次完成，写入 step/end
  → AgentLoop 按结束条件退出，写入 turn/end
```

它结束的是当前 turn，不是 Session，不会销毁 Agent 或退出 Host。成功路径通常无需再调用模型补一段自然语言总结。

原有工具用于特定 workflow 子 Agent 激活。后台通过标准工具注册入口复用同一捕获实现，并在每轮前创建独立包装实例；不修改原 workflow 分支的适用条件或 AgentLoop。

需要补齐的是真正逐轮可用的契约：

- 每轮初始化捕获状态，结束后结算，下一轮重新可用。
- 提交失败不能更新下次时间或投递消息。
- 现有 ConcludeTurn 会等待当前批次的其他工具完成；若已有 next-step 输入，循环还可能继续。这不等于无条件终止标记。
- 由外部服务为每次普通运行准备捕获状态，并在 `RunNext` 返回后处理已提交结果；不修改 AgentLoop 来增加一种强制结束状态。新的唤醒请求在前一轮返回后才由服务接纳；普通资料变化不通过 steer 向该后台 Agent 注入 next-step 消息。
- Agent 只有文本结束而没有成功的结构化结果时，应视为运行失败，不能用字符串猜测是否触达，也不能解释成 AI 决定取消下一次检查。运行失败、模型不可用和用户关闭属于运行状态，不是正常结果中的 `nextCheck: null`。

这些放在外部驱动器、Agent 组装和标准结束工具中完成。继续调用已有 `ConcludeTurn`，保留它等待工具批次及处理 Inbox 的既有语义；不为后台用途改动核心执行流，也不新建结果解析模型。

## 8. 主动服务如何投递

本轮按用户确认的方式，复用 Agent 内部消息格式：

```json
{
  "id": "<message-id>",
  "role": "user",
  "source": {
    "kind": "agent-message",
    "form": "relay",
    "senderSessionId": "<proactive-session-id>"
  },
  "content": [
    {"type": "text", "text": "<后台 Agent 已决定触达的内容>"}
  ]
}
```

它进入主会话 Inbox，领取后记录为 `user/message`。这不是伪造真人提问；实际来源由 `source` 明确区分。

| 后台决定 | 主会话发生什么 |
| --- | --- |
| `notify: null` | 不投递；主会话没有本次后台运行的内部消息、结束通知或新 turn |
| `notify` 有内容 | 投递一条 `agent-message`；主会话正常执行并向用户回复 |

**主动服务不产生 `subagent-settled`。** 普通子 Agent 的结束通知是另一条现有链路；如果主会话自己创建了普通子 Agent，它仍可能收到那条链路的 `subagent-settled`。

当前 `SendChildMessage` 的父子树授权检查不适合直接管理独立后台 Agent。因此复用消息构造和 Inbox 接纳基础，由 Go Host 验证本账号后台 Agent 的固定投递目标是本账号主会话，不把它伪装成普通 Fork 子 Agent。

主动服务默认向 next-turn 投递，主会话忙时等待，不使用 steer 改变当前用户工作的 step。这是该服务的交付选择，现有普通子 Agent 的 steer 行为保持原样。

## 9. 前端为何看不到内部消息

当前 `internal/httpapi/chat_transcript.go` 的公开投影过滤 `agent-message` 和 `subagent-settled`。它们都可能是日志中的 `user/message`，但不会作为用户气泡公开，也不是最初创建子 Agent 时已经返回的工具结果。

主动服务直接利用这一区分：

```text
后台 Agent 决定触达
  → 内部 agent-message（主会话日志和模型可见，用户气泡不可见）
  → 主会话正常生成 assistant/message
  → Web / 移动端通过现有 SSE 显示助手回复
```

主会话负责表达，不设置第二个“是否值得公开”的产品判断阶段。上一版的 `proactive_decide`、公开前草稿缓冲和主会话静默审核设计全部移除。

“直接投递”仍指向主会话的内部输入，不是绕开会话日志直接向浏览器插入一条后台研究文本。如果由主会话负责正常回复，仍有一次正常模型执行，但不承担第二次触达筛选。

后台工作过程始终留在后台 Session。其普通结束文本不会自动转发；只有成功提交的 `notify` 才触发投递。

## 10. 上下文连续性与重复信息

后台 Agent 有自己的持久会话，不是每次从空白上下文重建。它已有的历史、工具结果与上轮决定应继续利用。

### 10.1 其他会话内容放在哪

其他会话资料属于每轮判断使用的动态运行上下文。System 保存后台 Agent 的职责、行为规则和资料使用规则；其他会话的具体原文、时间、来源和片段作为运行时资料提供。现有长期记忆逐 step 注入 system 的行为继续沿用，不因本节改变。

`context` 不是新的 LLM role。可以复用已有 `RuntimeContextSource`，以 role 为 `user`、`source.kind: runtime-context` 的 `user/message` 进入模型视图。该来源不是用户发送的聊天输入，不显示为用户气泡。直接调取更多历史时，查询结果按普通工具结果进入上下文。

资料块应明确说明：这些是历史会话片段，帮助理解用户背景；它们不是用户此刻向后台 Agent 发出的新指令。区分真实用户要求、助手回答和资料引用，保留时间，不能把旧的请求误认为新任务。

### 10.2 每次 turn 都刷新，但不必重复追加同一份资料

在每个 turn 开始前，Go 重新收集一次受限范围内的最新会话活动。当前模型视图已经保留了相同资料时可以复用；有变化时追加新的运行时资料，标明其适用范围和更新时间。物理日志保持 append-only。

运行中出现新的会话活动时，可以在自然进入的后续 step 刷新；没有变化时不逐 step 再次扫描并重复注入，也不为了刷新资料强行启动 step。单纯“又采集了一次”的时间戳不能制造一次内容变化，否则每一步都会追加同样资料。资料自身保留原消息时间。

后台 Agent 的时间需求收口为：每个新 turn 的第一个 step 获得一条新鲜的标准 `time-context`。外部运行器在实际准备本次运行时触发一次采样，消息构造和提示文案复用现有实现，不另写“本 turn 开始时采样的时间”等文案，也不把当前时间再复制到 runtime-context。不要在 timer 刚到期或消息尚在等待时提前把那个时刻当成本次采样时刻。

其日志事件仍为 `user/message`，role 为 `user`，`source.kind: time-context`、`form: snapshot`，包括原有的时间格式、时区说明和经过时间文案。它不是新增事件类型，不是用户气泡，也不因其写入单独启动另一个 turn。

原 time-context 的调用位置与刷新判断继续照原规则运行；外部只补充本次运行所需的一次新采样，不改成 refresh=0 的每 step 采样。后续 step 仍可由原机制在满足刷新条件时提供新时间，原代码会根据最近已记录的 time-context 计算间隔。

标准消息构造已抽取为共享实现，`SampleTimeContext` 只采样、不写日志也不唤醒。外部运行器在其独占管理的后台 Agent 空闲时，通过原 `InjectMessage` 接纳这条标准时间消息，再接纳本轮唤醒输入并调用原 `RunNext`。原流程先确保 system，再领取 Inbox；因此首个模型请求可见新时间，原周期刷新也可识别刚领取的时间而跳过重复注入。已有测试验证连续两轮在十分钟内各补一次、普通第三轮仍遵守刷新间隔、v4 日志关系合法。Host 实际驱动接入仍在实施；不改 AgentLoop 主体。

现有 `ensureRuntimeContext` 会比较当前模型视图中最近的运行时资料；内容相同则跳过，变化或 compaction 后原资料已不在模型视图中则重新提供。它不是自动删除旧消息的机制，应明确新资料对同一范围的旧资料具有时效优先性。

### 10.3 收集范围：活动概览与按需检索

不是全量搬运其他会话，而是分两层：

```text
Go 提供最近活动会话的有界原文概览
             ↓
AI 根据当前背景选择值得深入的方向
             ↓
用 session_search 按关键词、sessionId、消息锚点展开
```

自动采集采用确定性的数据选择规则；业务相关性和研究价值由 AI 判断。建议初始默认规则：

| 规则 | 建议 |
| --- | --- |
| 账号范围 | 只采集同一账号的用户可见、未归档会话；主会话同样受近期活动范围约束，不在“其他会话”中重复列出 |
| 排除项 | 排除内部主动服务会话、普通隐藏子会话、system、内部 Agent 投递、工具调用、工具结果、执行状态与流式增量等过程记录 |
| 时间窗口 | 主会话和其他会话都只自动采集最近 7 天有实际用户/助手对话活动的部分；长期不活跃的会话不自动补入 |
| 会话数量 | 按最近实际对话活动时间选取，默认最多展开 8 个其他会话；超过时标明截断，未展开的历史仍可通过 session_search 查询 |
| 每个会话 | 优先提供最近四组真实用户输入及相关助手文本（每组最多两条助手文本）；有 Schedule 生成的可见结果时标明其来源，避免只有助手结论没有任务背景 |
| 消息大小 | 原文片段建议单条不超过 1,000 个 Unicode 字符，保留截断标记；不把截断文本称为完整摘要 |
| 全局大小 | 跨会话活动资料建议最多 30,000 个 Unicode 字符，达到预算时减少或截短片段 |
| 覆盖说明 | 告知时间范围、实际包含数量、是否还有未包含会话及片段截断情况；不让模型误以为看到了全部历史 |

这些数值是待验收调校的采集默认值，不是用户必须配置的环境变量，也不限制 AI 继续检索的历史范围。最初采用真实文本片段，不在每轮前为所有会话额外调用一次摘要模型。

每个片段至少保留 `sessionId`、标题、消息角色、消息时间、日志 `seq`、原文及截断标记。 提供给后台 Agent 的活动资料中，消息时间、会话最近活动时间及采集范围起点统一格式化为带 `UTC` 时区的可读绝对日期时间（例如 `2026-11-24 09:30:00.000 UTC`），不直接注入 Unix 毫秒数字。底层日志和 SQLite 索引仍保留原有毫秒时间戳。历史资料明确标注时间属于原会话；后台当前时间仍由自身标准 `time-context` 提供，不复制其他会话的时间提示为当前时间。AI 可以据此继续读取锚点前后内容，而不是只能看到一个不可追溯的摘要。

最近窗口会遗漏更早的重要背景，这是有界自动采集的取舍。较早的主题可由长期记忆、已有研究历史、Schedule 或新线索提示 AI，再通过历史检索找回。没有近期会话变化时仍可到时研究，不把这份活动列表当作唯一信息来源。

活动时间使用实际已提交的对话消息时间，不用会话创建时间、前端打开时间、SSE 重连、Host 恢复或磁盘文件修改时间代替。主会话没有近期交流时，只保留其投递目标等必要运行身份，不为填满资料窗口搬运很久以前的正文。

### 10.3.1 采集的是对话资料，不是执行轨迹

正文采集只取真实用户输入和用户可见的助手文本。不能仅判断 event 为 `user/message` 或 `assistant/message` 就整条复制：前者可能是内部上下文/Agent 投递，后者可能包含工具调用块。

- 用户消息仅采集真实对话来源的正文；不把 runtime-context、time-context、agent-message、subagent-settled 等内部输入当作用户交流。
- 助手消息提取对话文本，过滤 tool-call、推理过程和机器执行信息；不复制整条原始消息 JSON。
- 工具执行过程中的提示文本不单独作为一组新的用户交流；选片段时优先真实用户输入与相关助手结论。
- 不采集 `tool/call`、`tool/result`、step/turn 执行轨迹、审批状态、Job 输出或调试日志。
- 图片/文件按需要保留存在性、名称和定位引用，不把二进制、附件正文或全部文档内容自动注入；需要时通过相应读取能力获取。

这是有界对话采集器的明确过滤契约，不是让后台 Agent 自己从整份执行日志中删选。

### 10.4 增量、重复与 compaction

首次取得某个会话时提供所选片段；后续如果当前模型上下文仍保留它们，优先补充新增消息或实际状态变化。允许为了连贯提供少量相邻旧消息，不维护“每条消息只准出现一次”的硬规则。若继续复用现有整体 snapshot 机制，变化时可重新提供一份有界活动概览；不能把只有增量的片段错误标成对全部旧资料的完整替代。是否采用分段更新，在实现设计中明确。

是否需要再次提供，应结合当前模型视图判断，而不仅是磁盘上曾记录过某个 `seq`。compaction 后细节可能已经不在模型视图中，允许重新提供有界概览或由 AI 按锚点取回。初期可先复用现有运行时资料比较，避免为了增量立即增加一张永久“读过哪些消息”的数据库。

组织原则：

1. 模型当前上下文已保留的信息，不每轮整包重复注入。
2. 新交流、最新状态和变化信息有来源与时间，按需要补充或刷新。
3. 已保存物理日志不代表内容仍在 compaction 后的模型视图中；需要关键事实时允许再次补充。
4. 可以在新一轮重新梳理当前情况，不能为避免重复而禁止必要的最新整理。
5. 主会话全部历史不默认复制；后台能按需检索和获取相关背景。
6. 自己的研究输出不自动变成 USER.md 中的用户偏好，也不额外写一份长期记忆快照。

### 10.5 当前接口的实际边界

当前 `session_search` 无参数浏览返回最近会话信息；按会话读取返回有界的首尾原文，按锚点可读前后片段。它不是现成的“最近 N 天的增量活动聚合”接口。

当前关键词查询的 `after` / `before` 比较的是会话创建时间 `s.created`，不能直接拿它筛选最近消息更新时间。采集层需要依据已提交可见消息的时间和序号，从现有日志投影或 SQLite 消息索引读取。可以补充 Go 内部的活动查询方法；不新增第二份会话正文存储，不在本轮修改现有工具参数语义。

现有普通会话列表只排除了普通子会话和归档记录。未来独立后台会话还需要按内部用途明确排除，不能因为它不是普通子 Agent 就意外纳入用户会话概览和全文索引。

活动采集器的基础实现已加入现有 SQLite 索引模块：按消息时间读取最近 7 天、主会话与最多 8 个其他会话，提供最后四组用户交流与有界助手文本，单条 1,000 字、总计 30,000 字，保留 seq 与截断标记。已测试内部来源/工具块/欢迎语排除与归档移除；Host 运行时刷新接入仍在实施。

### 10.6 后台 Agent 需要感知的信息清单

| 信息 | 初始组织者 | 更新时机 | 模型中的位置 / 获取方式 |
| --- | --- | --- | --- |
| 后台身份、主动服务职责、资料使用规则、结果提交要求 | Go Agent 组合 | 创建/恢复时组装；定义变化按组合规则处理 | System；工具具体参数以真实 schema 为准 |
| 当前长期记忆 USER.md / MEMORY.md | 现有 Go 记忆模块 | 每个模型 step 按现有机制读取当前值 | System，保持当前项目行为 |
| 当前实际工具定义 | Go 组合及已启用贡献 | 每 step 准备真实工具表；本 step 内保持一致 | 模型请求的 tools 字段，不把全部 schema 再抄到 system |
| 适用的 Skill 名称与描述 | Go Skill 发现与组合选择 | 首次需要及目录变化时 | 现有 Skill catalog 上下文；完整内容通过 skill 工具读取 |
| 后台自己的会话历史 | 原有 Session 模型视图 | 随自身消息、工具结果和 compaction 演进 | 原有 user/assistant/tool 消息，不另复制为“背景资料” |
| 本次触发原因、涉及位置和触发时间 | Go 唤醒输入 | 本次 turn 开始 | 内部来源的输入，只携带触发信息与定位 |
| 当前时间与已知时区 | 外部运行器补充一次标准 time-context；原时间机制继续运行 | 本次首个模型请求前补充新采样，之后按原刷新规则处理 | `user/message`、`source.kind: time-context`；消息格式和提示文案复用现有实现，不在 runtime-context 另写时间 |
| 当前有效的下次检查时间及其理由、最近已提交的检查结果 | Go 从后台日志/运行状态读取 | turn 开始；结果成功提交后更新 | 运行时资料；模型视图已有的同一结果尽量复用，compaction 后可恢复关键部分 |
| 主会话及其他会话的新交流、近期活动 | Go 活动采集器 | turn 开始；收到真实变化信号后在后续 step 刷新 | 有界 runtime-context，原文只经这条采集路径进入；更早细节通过 session_search |
| 当前 Schedule 工作安排及近期投递概况 | Go Schedule 服务 | turn 开始取概览；安排变化后刷新；需要时查询 | 运行时概览 + schedule_list/view 工具结果；由 AI 理解业务关系 |
| 主会话标识、当前工作目录、正在执行/排队的基本状态 | Go Host / Session | turn 开始及相关状态变化时 | 运行时事实；不能据此推测用户现实中是否空闲 |
| 可用插件能力、已经确定的授权可用性或错误 | Go 当前实际贡献和插件自身报告 | 启停/授权状态变化、调用失败时 | 能力与状态信息；不把 API Key、Token 或 CLI 凭证正文塞入上下文 |
| 外部变化线索，例如新的邮件/日历信息 | 支持该功能的插件 | 插件收到或采集到信息时 | 有界、带来源和时间的资料；完整内容由相应工具按需读取 |
| 网页正文、历史详细内容、文件与图片内容 | 后台 Agent 选择工具 | Agent 判断需要时 | 普通工具结果/现有附件块；不在每轮前自动遍历并加载全部内容 |

System、运行时资料、原会话消息、Skill catalog 和工具定义各有组织入口，不重复表达同一批正文。后台会话中已经保留的研究结果和下一次安排，不每轮重新全文包装一遍；只有需要补齐当前模型视图或状态确有变化时刷新。

### 10.7 “实时获取”的边界

实时感知是指 Go 能记录变化，并在下一次模型 step 组织请求时提供最新已提交的信息。已经发给模型的那一次请求不能在执行途中插入新的上下文；无需每个事件都中断它重开一个 turn。

“记录变化”不等于立即发起新的后台 turn，也不向 Inbox 注入 steer 消息来制造一个后续 step。后台没有在运行时，普通资料变化等待变化路径的 10 分钟稳定窗口和 30 分钟最小间隔；AI 选定的时间若先到达，则由那条独立路径运行并采集这些资料。

会话、记忆、Schedule 和能力状态等使用本地已知事实；外部邮箱、日历、网页等只有在插件确实提供事件或 Agent 主动调用读取工具时才能更新。已安装插件或持有 OAuth 凭证本身不等于持续订阅全部第三方变化。

信息都有时间、来源和必要的覆盖/截断说明。模型明确知道哪些是当前状态，哪些是历史记录，哪些只是尚待展开的线索。采集失败时如实标记不可用，不把空结果伪装成“确认没有新信息”。

## 11. 主动服务是否插件化

建议 **主动服务运行机制内置 Go，外部能力由插件扩展**。

它需要控制 timer、持久 Agent 运行、结果确认、Session 恢复和主会话 Inbox 投递。这些都属于我们已经选择由 Go 管理的核心能力。让它成为普通 Cordis 业务插件，会把这些核心责任再次跨进程搬到 Node。

插件继续提供第三方信息、工具、Skill 和可选事件提示；它们通过内置服务交互，不控制 AgentLoop 或接管后台 Agent 的生存期。Agent 组合能力也在 Go 装配层实现。Go 装配与插件边界见[架构说明](architecture.md)，初始组合与运行契约见第 13 节；通用 Preset 子系统已通过同一 Go Registry 实施，见[设计与实施记录](agent-preset-go-plan.zh-CN.md)。

## 12. 数据、启停与边界

- Redis 用户 Hash 可保存主动服务开关；Controller 同步设置和代理状态。
- Host 本地保存后台 Session 定位、下一次运行状态和必要的交付恢复位置；沿用 `/root/harness/.dsh/storages/` 与既有 volume/NAS。
- 变化路径在同一份本地运行状态中只保存待检查标记、最近变化时间和最近一次后台实际运行开始时间，恢复后可继续计算 10/30 分钟条件。不保存变化正文、内容差异、逐消息待办列表或每话题任务记录。
- 检查事实和结构化结果以后台日志为准；下一次时间是成功结果的运行状态投影，缓存丢失可据最后成功结果恢复。
- 同一次投递中断时沿用已保存的 messageId 恢复，不重新伪造一次业务触达。这属于 I/O 恢复，不做业务相似性判断。
- 主会话模型已有有效选择时沿用它；尚未选择时可解析账号的有效默认端点；已选模型失效时明确暂停，不悄悄替换。
- 没有可用模型时功能等待配置，不阻止 Host 或前端启动；模型配置更新提供重评触发。
- Go 对并发、执行时长和调用预算设置运行边界，具体默认值在实现验收时确定，不用它们替代 AI 选择检查时机。
- Host 停止即停止主动服务；Controller 不为到期的主动检查自动重建 Host。
- 关闭主动服务停止未来判断和当前后台运行，不取消用户 Schedule，也不撤回已经公开的回复。
- 暂不考虑手机系统推送、安卓后台保活或新的消息通道。

实现遵循上述边界，不新增用户任务表、每话题跟进表或独立记忆系统。

## 13. 实施收口与验收契约

1. **Agent 组合**：普通组合维持原有能力。Go 内置后台 Preset 使用 `go-bot-proactive` 组合，仅排除问答（askuserquestion）、退出 Plan 模式、Goal 管理、子 Agent/工作流及其配套控制工具（含给其他 Agent 的 send_message），以及 Schedule 创建/修改、文件交付工具 present。其余当前可用工具和已启用插件能力、Skill 全部保留，包括文件读写、Shell、记忆、历史检索、网页搜索、浏览器和 readimage；未启用或未配置的能力不会因 Preset 自动启用。Schedule 保留 list/view，下次自主检查只由后台专用 structured_output 安排。初始装配和动态加载的工具使用同一筛选规则，不新增后台专属外部操作分类或拦截策略；实际调用仍经过原 Go 工具执行管线、权限和沙箱。Skill 不增加后台专属排除范围，目录、加载与显式调用沿用现有机制。后台可保存研究文件，但不使用 present 直接交付文件；是否触达主会话仍通过 structured_output 的 notify 决定。
2. **上下文**：后台拥有自己的持久历史；实时来源使用已有 RuntimeContextSource 的整体有界 snapshot，不冒充增量。新 turn 开始采集；有真实变化时在自然后续 step 刷新。固定窗口和预算采用第 10 节默认值，不增加用户 env 参数。
3. **时间**：外部运行器在本轮首个模型请求前补一次标准 time-context，抽取并复用现有构造逻辑；后续仍使用原 10 分钟刷新规则。不得修改 AgentLoop 的运行顺序、结束条件或 Inbox 语义。
4. **结果**：每轮准备独立捕获状态，通过标准工具注册机制提供 structured_output。三个字段均必填；nextCheck 必为未来时间和理由的对象，notify 可为空。校验失败不结束 turn。工具结果成功提交且 RunNext 正常返回后，Go 结算本轮，保存时间并按决定投递；不增加另一次解析 LLM。
5. **投递**：只向本账号主会话 Inbox 的 next-turn 提交 agent-message，公开 UI 仍只展示主会话生成的助手回复。记录投递 messageId 用于中断恢复，不引入业务去重。安静结果不投递任何消息或结束通知。
6. **状态与设置**：Redis 用户 Hash 中的主动服务开关默认为关闭；用户开启时，Controller 先校验主会话已选模型，未选择时校验账号默认模型。缺少或失效时返回 409，不保存启用状态，Web/移动端弹窗提示并提供模型设置入口。校验只检查配置，不调用模型。关闭不依赖模型。关闭期间不准备后台 Agent、不运行检查；Host 持久化独立 Session 定位与恢复所需状态，不保存另一份对话正文。Web 显示开关、下一次检查及运行异常；移动端 Release 保留简洁开关和需要处理的配置/异常提示，Debug 才显示下一次时间、理由、最近完成和诊断状态。不提供“立即运行”。开启后若模型配置失效则暂停等待修复，不阻塞登录与主会话。保存模型配置不会自动打开已关闭的开关。
7. **异常**：既有模型重试仍由原执行机制处理。turn 最终失败或没有结构化结果时显示错误，保留最后成功决定，不能把失败当作取消检查，也不能因一个已过期 timer 进入空转循环。后续有效变化、模型恢复、重新开启或 Host 恢复可提供新的执行机会；不得伪造一个成功决定或业务检查周期。
8. **验收**：测试四类触发互不错误限流、跨触发消费旧变化/保留新变化、每轮结果与非空未来时间校验、隐藏内部 Session、近期可见消息采集、标准时间上下文、仅 notify 投递、恢复和关闭。用本地真实模型与 Web/Android 验证；检查 AgentLoop/工具管线主体未被修改，ECI 暂不验收。
