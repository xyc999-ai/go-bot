# 会话交付视频展示方案

状态：已实现 Web 与移动端展示，并完成 Chrome 与 Android 模拟器交互验证。

## 1. 目标与当前基础

AI 通过现有 `present` 交付视频文件，Web 和移动端将其显示为可在会话中播放的视频。提供播放、暂停、拖动进度、静音和全屏操作，并与现有图片、工具卡片和普通文件保持一致的视觉语言。

当前基础：

- 会话公开投影中的文件块携带 `file.source = presented` 和 Host 文件路径；前端通过 HTTP 请求文件内容，SSE 只传消息和文件引用。
- `groupDisplayBlocks` 已将连续交付图片变成图片行，其他文件仍为下载卡片。
- Host 文件接口使用 `http.ServeContent`，具备 Range 分段读取基础；Controller 使用反向代理。
- Web 文件和图片目前通过带 `X-User-ID` 的 fetch 获取 Blob。该方式不适合用作视频的默认播放链路。
- 移动端已安装 `expo-video`，插件教程已使用它，不需要再引入另一套视频播放器库。

本次保持现有 `file` 块、present 工具、会话日志和 SSE 协议。视频是前端的展示分类，不是新增模型内容块类型；不新增视频专用工具、Redis 数据或转码服务。

## 2. 识别与分组

### 识别

仅对显式交付的 `presented` 文件尝试视频预览，优先覆盖 `.mp4`、`.webm`、`.mov`、`.m4v`，扩展名不区分大小写。扩展名用于决定尝试哪一种展示，实际能否播放由播放器判断；容器扩展名不保证设备支持其中的编码。

不解析助手 Markdown 链接或裸路径来生成播放器。用户上传附件的展示规则本次保持现状。

### 顺序与边界

每个视频文件独立占一行，连续视频沿正文左边界纵向排列，不合并成横向滑动组。图片仍保留现有横向图片行；视频与其他内容严格按照原始内容块顺序展示。

| 原始顺序 | 展示 |
| --- | --- |
| 视频 A、视频 B、视频 C | 三个单视频行，依次纵向排列 |
| 视频 A、文档、视频 B | 视频行 A → 文档卡片 → 视频行 B |
| 视频 A、图片、视频 B | 视频行 A → 图片行 → 视频行 B |
| 视频 A、文本、视频 B | 视频行 A → Markdown → 视频行 B |
| 工具、视频 A、视频 B、工具 | 工具组 → 视频行 A → 视频行 B → 新的工具组 |

若两次 present 调用之间存在一个工具块，就在两个视频之间保留该工具块；一次 present 交付多个视频，也逐条独立成行。视频块仍会打断前后普通工具的连续分组，不隐藏工具或改变顺序。

`present` 调用仍使用当前工具卡片，下面的视频是交付结果，不重复增加一套“生成视频”工具标题。图片查看工具组保持原样。

## 3. 会话内的视觉设计

采用轻量视频框，与现有图片预览左边界一致，不再包一层大卡片。

| 项目 | Web | 移动端 |
| --- | --- | --- |
| 视频框宽度 | 消息可用宽度的 100%，最大约 560 CSS px | 助手消息可用宽度的 80%，左对齐；例如可用宽 360 dp 时，视频约 288 × 162 dp |
| 固定画幅 | 16:9，高度由实际宽度计算 | 16:9，高度由实际宽度计算 |
| 圆角 | 12 px | 12 dp |
| 连续视频单元间距 | 16 px，包含文件名行之后的留白 | 16 dp，包含文件名行之后的留白 |
| 画面适配 | 完整显示原比例，不匹配画幅时留黑边 | 完整显示原比例，不匹配画幅时留黑边 |
| 多个视频 | 一行一个，纵向排列 | 一行一个，纵向排列 |

以上为实施时的起始尺寸，最终结合 Taste Skill 的比例、留白和视觉层级，以真实双端截图校准。视频比现有图片缩略图明显更宽，便于直接在会话内观看；在窄窗口或小屏上随消息可用宽度收缩，始终保持 16:9，不引入页面整体等比缩放。竖向或方形视频在统一画幅内完整显示，全屏时再充分利用屏幕。

未播放时展示真实视频首帧，中央一个白色播放图标，下方角落显示已获取的时长。首帧尚未取得时先显示安静的深灰画面和播放入口，不伪造封面，也不要求后端为此生成缩略图。

右上角固定全屏入口，图标使用现有 Lucide 线条风格。图片内容明暗不定，覆盖按钮使用小面积半透明黑底和白色图标；不引入新的品牌强调色、重阴影或额外装饰。

文件名在播放器下方一行显示，过长省略，右侧为下载按钮；可带已有文件描述，但不重复显示路径。视频内置控件不会挤占正文布局。

视频行不使用横向换片、方向箭头或边缘渐隐；这些仍仅属于现有图片行。视频底部可使用轻薄的暗色渐变承载播放控件，保证进度和按钮清晰。拖动视频进度条时，该手势由播放器处理，避免误触页面滚动。

## 4. 播放交互

### 会话内

- 默认不自动播放，不循环、不自动播放下一条。
- 点击播放按钮后，在原位置播放，不自动进入全屏；初次有声播放由用户点击发起。
- 暂停时显示中央播放按钮；播放时提供底部播放/暂停、时间、进度条和静音入口。
- Web 鼠标进入或键盘聚焦时显示完整控制层，离开且播放中时约 2 秒淡出；暂停、加载或拖动时保持可见。
- 移动端播放时点画面显示或隐藏控制层，播放/暂停用明确按钮操作，避免一次点击既显控件又暂停。右上角全屏入口在控制层隐藏时也保留。
- 全部操作有无障碍名称；移动端图标可见面积保持轻量，点击区域至少 44 dp。
- 播放到结束后停在末帧，显示重播入口。
- 同一客户端同时只播放一个视频，开始另一条时暂停之前的视频。切换会话、切换导航页、App 进入后台或播放器完全离开可见区时暂停。

### 全屏

采用应用内黑底全屏查看器，而不是依赖系统播放器承担所有交互。Web 使用覆盖视口的查看器；移动端使用全屏页面/Modal，与现有图片全屏的黑底语言保持一致。

- 点击会话视频右上角全屏按钮进入；保留当前播放位置及播放/暂停状态。
- 视频按原始比例居中完整显示。横屏和竖屏均可查看，不强制旋转手机。
- 左上角提供关闭按钮，底部提供完整播放控制；Web 支持 Esc，Android 返回键关闭。
- 点击视频之外的黑色留白直接退出；点击视频本体仅操作播放或控制层，点击/拖动控制条不会触发关闭。
- 如果视频铺满屏幕没有留白，仍可用明确的关闭按钮退出。
- 退出时暂停，返回会话中的原视频及原滚动位置，保留进度；需要继续播放时点击播放。
- Web 全屏进入采用约 180 ms 淡入，退出直接恢复原会话位置；移动端使用轻量淡入淡出。尊重减少动态效果设置，不制作飞入、旋转或弹跳动画。

全屏和会话内使用同一播放状态与播放器，不同时运行两个有声实例。移动端切换时只挂载一个有效 VideoView，避免同一原生播放器同时绑定两个视图。

## 5. 加载、失败与下载

- 仅在视频接近可见区时准备媒体源，按需请求元数据/首帧；不为所有历史视频同时创建和预加载原生播放器。
- Web 使用 `preload="metadata"` 作为预加载提示。浏览器可自行决定实际读取量，不能把它当作严格的流量上限；播放器可见性和挂载范围仍需由客户端控制。
- 点击播放后才进入正常缓冲和分段读取。缓冲时保留当前画面，显示小型加载反馈，不让视频框反复塌陷、跳动。
- SSE 重放或最终 assistant/message 更新不重建同一个视频播放器；使用稳定块标识保持当前播放进度。
- 网络失败显示“视频暂不可用”及重试、下载；编码不支持显示“当前设备无法播放此视频，可下载后打开”。不把一次预览失败判作整个文件已损坏。
- 下载仍走原有显式下载流程。移动端点击下载后才保存到本地文件区，身份继续使用账号与后端路径；浏览或播放不会把视频加入本地文件区。
- 本次不增加本地视频工作区，也不自动写入手机相册；本地文件区已有分享流程继续可用。

## 6. HTTP 播放链路

播放字节由普通 HTTP 提供，SSE 只通知文件块出现：

```text
present 成功 → 现有会话投影/SSE → 前端识别 file 为视频
    → 播放器请求 Controller 的文件内容地址
    → Controller 代理到该账号 Host
    → Host 读取原工作区文件，返回媒体内容或 Range 分段
```

目前 Web 的 `<video src>` 无法使用 fetch 那样的自定义账号请求头，因此需要一个限定在媒体读取上的小调整：

- 复用现有会话文件内容接口；为直接媒体读取允许通过查询参数携带账号标识，例如 `GET /v1/sessions/{sessionId}/files/content?path=...&userId=...&inline=1`。
- 该查询账号只用于此 GET/HEAD 文件读取入口，不扩展为所有 API 的通用账号参数。普通 API 仍用 `X-User-ID`，Controller 仍负责选择 Host，并使用现有 Host Token 访问 Host。
- 账号名仍是当前系统的路由标识，不将此 URL 描述成授权令牌。文件依然按原会话实际工作目录和已有路径检查打开，不扩大可读取范围。
- `inline=1` 对支持的媒体响应使用正确 Content-Type 和 inline disposition；正常下载仍保留 attachment disposition。
- 保持 Range / If-Range 请求和 206 / Content-Range / Accept-Ranges 响应经过 Controller；补齐 GET/HEAD 路由，并实测拖动进度，不仅检查响应头。
- 移动端沿用相同文件源，使用 expo-video 已支持的请求 headers 传递账号。

不采用先将视频整体 fetch 成 Blob 再播放的默认路径，不把完整视频塞入 SSE，也不要求前端直连 Host、云存储或第三方生成服务。

## 7. 实施与验证边界

实施分工与验证范围：

1. 共享展示层增加视频识别及独立视频展示项，每个视频占一行，保留所有原始内容顺序。
2. 验证并补齐文件的 inline/HEAD 与 Controller 账号路由，确保真实 Range 播放。
3. 接入 Web HTMLVideoElement 和移动端现有 expo-video，完成会话内及黑底全屏交互。
4. 使用固定视频素材驱动真实 Controller → Host → SSE → 前端，不需要调用付费模型生成测试视频。
5. 分别检查双端真实截图及录屏：单视频、连续多个视频逐行展示、视频与图片/文档/工具/文字混排，固定 16:9 画幅中的横竖视频，宽窄消息区，播放/暂停/拖动/静音，全屏进出和背景点击，滚动/切会话暂停，重放不重置，损坏/缺失/不支持编码时回退，以及下载不会自动入库。
6. Web 验证明暗两套主题；移动端验证 iOS 与 Android 播放行为，不为此更改现有页面字体或屏幕适配规则。
